# One binding per OS, whatever the CPU

Can the bindings generated by jextract on one CPU serve the other CPUs of the same OS, so that PanamaGL ships a single binding per OS instead of one per OS and CPU?

**Yes, on Windows, Linux and macOS.** The bindings generated on x86_64 and ARM64 only differ on declarations that PanamaGL does not use, and the tests of PanamaGL already pass on ARM64 with the x86_64 bindings of Windows and Linux.

## Why it works

The bindings generated by jextract describe the C declarations of the headers : function names, struct layouts and function descriptors made of C types. They do not encode any calling convention : the native linker of the Foreign Function and Memory API (`Linker.nativeLinker()`) applies the one of the CPU running the JVM when a downcall is invoked, including for variadic functions.

A binding hence depends on the CPU only where the headers do, i.e. where they declare something differently for each CPU. Windows (LLP64), Linux and macOS (LP64) have the same data model on x86_64 and ARM64, so the OpenGL, GLU, GLUT, GLX, WGL and CGL declarations are the same on both CPUs.

## Generated bindings, x86_64 vs ARM64

The [Bindings per CPU](../.github/workflows/bindings-per-cpu.yml) workflow generates the bindings of each OS natively on a x86_64 and an ARM64 GitHub runner, with the same jextract, libclang and headers, then compares them declaration by declaration with [compare_bindings.py](../.github/scripts/bindings/compare_bindings.py). The headers are the ones of the scripts of [panama-gl-bindings](https://github.com/panama-gl/panama-gl-bindings/tree/main/scripts).

| OS | Runners | Packages | Declarations | Identical | Different or only on one CPU | Used by PanamaGL |
|---|---|---|---|---|---|---|
| Windows | `windows-latest`, `windows-11-arm` | `wgl`, `freeglut` | 47 817 / 47 979 | 47 647 | 419 | none |
| Linux | `ubuntu-24.04`, `ubuntu-24.04-arm` | `opengl`, `glext`, `glx`, `glxext` | 12 888 / 12 886 | 12 863 | 25 | none |
| macOS | `macos-15-intel`, `macos-latest` | `opengl`, `glext`, `cgl` | 4 180 / 4 242 | 4 173 | 72 | none |

The declarations of the largest package of each OS are counted. The declarations that differ are :

* **Windows** : the low level parts of `winnt.h` and of the compiler intrinsics : `CONTEXT`, `DISPATCHER_CONTEXT`, `RUNTIME_FUNCTION` and the other exception unwinding structures, `SLIST_HEADER`, `XMM_SAVE_AREA32` (x64) or `NEON128` (ARM64), and the intrinsics such as `_InterlockedCompareExchange`, `__readgsqword` or `__cpuid`, which no DLL exports. Nothing in `user32`, `gdi32`, `opengl32`, WGL or freeglut.
* **Linux** : glibc internals : `pthread_mutex_t`, `pthread_attr_t` and the other `pthread_*` types, `wchar_t`, `nlink_t`, `blksize_t`, `__WORDSIZE` related macros.
* **macOS** : the `TARGET_CPU_*` macros, the `__DARWIN_*` macros of the 64-bit inode and 10.5 symbol variants, and `__darwin_va_list`. The two macOS runners also have different SDKs, hence the different `__MAC_*` and `__IPHONE_*` version macros.

A struct of OpenGL, GLX, X11, WGL, Win32 or CGL containing one of these types would differ too, which none does.

## Tests on ARM64 with the x86_64 bindings

Before 1.3.1, `GL_windows_arm` and `GL_linux_arm` already extended `GL_windows_x64` and `GL_linux_x64`, i.e. used the bindings generated on x86_64. The [CI](../.github/workflows/ci.yml) of `main` ran all the tests on the six runners :

| `windows-11-arm` | `PanamaGLFactory_windows_arm` | 4.6 Mesa 26.2.4 (D3D12) | 182 (no JavaFX) | 0 |

The macOS x86_64 bindings (`opengl.macos.x86`, `glext.macos.x86`, `cgl.macos.x86`) were the ARM64 ones with another package name, and the `GL_macOS_x64` wrapper was `GL_macOS_arm` with another package name.

## A single binding per OS, since 1.3.1

* **Bindings** : `panama-gl-bindings` 1.3.1 has one package per header set and OS, without CPU name (e.g. `opengl.macos` instead of `opengl.macos.arm` and `opengl.macos.x86`). The macOS bindings are divided by two (jar of 1.9 MB).
* **Wrappers** : one `GL_<os>`, `PanamaGLFactory_<os>` and `PlatformMatcher_<os>` per OS in `panamagl.platform.<os>`, instead of `GL_<os>_x64`, `GL_<os>_arm` and their factories, platform matchers and tests. `PlatformMatcher_<os>` accepts the 64-bit CPUs PanamaGL is tested on (`amd64`, `x86_64`, `aarch64`, `arm64`). `GenerateAPI` writes one wrapper per OS.
* **CI** : [tested_platforms.py](../.github/scripts/tested_platforms.py) fails if the factory of an OS was not tested on both a x86_64 and an ARM64 runner.

Beyond the CPU, the packages of an OS largely overlap, since each one is generated from headers including the others :

* **Linux** : `glext` is `opengl` (Mesa's `gl.h` includes `glext.h`), `glxext` is `glx` (`glx.h` includes `glxext.h`), and `glx` contains `opengl` except GLUT and GLU. A single binding of `glut.h` and `glx.h` contains all the declarations of the four packages : 17 MB of sources instead of 65 MB, 7 150 classes instead of 25 580, and a jar of 6.7 MB instead of 23.3 MB (generated on Linux x86_64 with jextract 23, compiled for JDK 25). PanamaGL does not use `glxext`.
* **Windows** : `wgl` (71 MB of sources) and `freeglut` (30 MB) both declare `windows.h`. A single binding of both header sets would be about the size of `wgl`, and smaller with `WIN32_LEAN_AND_MEAN`, which excludes the COM, OLE and RPC headers that PanamaGL does not use (not measured).

## One glext binding for all OS, since 1.4.0

The function pointer types of the OpenGL functions (e.g. `PFNGLGENBUFFERSPROC`), through which the wrappers invoke the functions they resolve at runtime with `wglGetProcAddress`, `glXGetProcAddress` or the symbols of the OpenGL framework, do not bind any symbol : they only describe the signature of a function. They were used by the wrappers of all OS from the Linux binding, generated from the headers of Mesa.

The [glext per OS](../.github/workflows/glext-per-os.yml) workflow generates the Khronos `glext.h` and `khrplatform.h` with jextract 22 on Linux, Windows and macOS, then compares them with `compare_bindings.py --resolve-layouts`, which replaces the C type layouts by their definition on each OS (e.g. `C_LONG` is a `JAVA_INT` on Windows, a `JAVA_LONG` on Linux and macOS) :

| OS | Declarations | Identical | Different |
|---|---|---|---|
| Linux vs Windows | 7 873 | 7 873 | 0 |
| Linux vs macOS | 7 873 | 7 850 | 23 |

The 23 declarations that differ are the function pointer types using `GLhandleARB` (`ARB_shader_objects`), an `unsigned int` except on macOS, where it is a `void*`.

`panama-gl-bindings-glext` (package `opengl.glext`) hence contains the function pointer types and constants of the Khronos `glext.h`, except these 23 types, which are in the Linux and Windows bindings, the only ones using them. `GenerateAPI` searches the function pointer types in `opengl.glext`, then in the package of the binding of the OS.

The Windows binding (`opengl.windows`) only contains OpenGL 1.1, GLU, freeglut, WGL and the Win32 declarations used by PanamaGL, instead of the whole `windows.h` : a jar of 2.1 MB instead of 31.5 MB.

## Generating the bindings with jextract

Two pitfalls appeared while generating the bindings with a jextract built from its sources, since no jextract build exists for Windows ARM64 :

* Since LLVM 16, libclang spells the cursors of unnamed records `struct (unnamed at <file>:<line>:<column>)` instead of an empty string. jextract then uses this spelling as a class name, which does not compile, as a file name, invalid on Windows, and as a field name, which fails on the anonymous structs of `winnt.h`. [patch_jextract.py](../.github/scripts/bindings/patch_jextract.py) restores the empty spelling. The only LLVM 15 release for Windows ARM64 (15.0.6) is built with assertions, which fail in jextract.
* The libclang of Ubuntu has an absolute resource directory : the builtin headers that jextract adds with `-I` then hide the system headers they include with `#include_next` (e.g. `stdint.h` is empty). The builtin headers of jextract are removed on Linux.

The workflow uses jextract 23 (commit `1e6737c`), LLVM 18 and JDK 25 on every runner. The committed bindings were generated by jextract 22, whose code differs (e.g. `findOrThrow` requires JDK 23), but not on what depends on the CPU.
